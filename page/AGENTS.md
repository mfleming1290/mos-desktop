# MOS Desktop frontend

- Purpose/owns: thin Vue shell around the approved compiled Battlemoon interfaces; `src/Plugin.vue` is the MOS entry, `DesktopShell.vue` is the projection, desktop modules own host command composition, static registration, geometry policy and layout intentions.
- Inputs: parent distribution/authorization boundaries, pinned `runtime/`, exact Clock/contracts 0.1.1 archives acquired by `scripts/prepare-components.mjs` from the existing public Clock release source. Do not copy private SDK implementation or hand-edit generated codecs.
- Invariants: one accepted snapshot and serialized dispatch; the WASM reducer alone changes semantic state. Vue refs hold snapshot projection and transient/config state, not a second semantic reducer. Static trusted factories stay outside DTOs. Window identity keys and stable host/config props prevent revision/order-driven remounts.
- Decisions: one workspace; About is single-instance; Clock has independent instances/configs. Restore from minimized means normal geometry. Minimize hides/inerts content while disposing Clock work through `active`; page visibility also suspends local work. Close-last-view disposes only its local app, never remote processes.
- Interaction: gestures retain pointer capture, preview locally, commit once, and cancel on Escape/cancel/lost capture/resize/route exit. Model focus drives intentional DOM focus; ordinary content updates must not steal it. Title/resize-handle arrows offer keyboard geometry controls; Alt+Shift+Left/Right/M/X handle focus/minimize/close.
- Persistence: trusted host `verifiedStorageScope` or the server-confirmed MOS profile id plus Web Locks required. `desktop-profile.mjs` uses the established MOS `authToken` only internally for same-origin GET `/api/v1/auth/profile`; never decode, log, export or persist credentials, or infer identity from stored userid/display names. Credential equality fences every layout read/write/flush, including disposal. Storage events and foreground identity checks reverify and remount; initial profile acquisition is bounded and cancelled on exit. Store bounded v1 intentions, not raw DTO snapshots or secrets; preserve invalid/future records and disable writes after failed reads/restores. Missing scope/locks or a second writer gives explicit memory-only behavior. This adapter is not standalone authentication. Existing localhost MOS profile response, credential presence and Web Locks were observed read-only; installed 0.1.3 autosave and cross-account behavior still require acceptance.
- Verification: parent build commands; `tests/desktop-*.test.mjs` exercise real reducer/controller, app identities, geometry and storage; `tests/public-runtime.test.mjs` mounts the built federation module with one host Vue, proves independent Clock sessions, configuration, preview commit/cancel, minimize/restore, cleanup, late fetch fencing and scoped restore. JSDOM is not actual MOS/native pointer evidence.
- Outputs: federation `./Plugin`, manifest and allowlisted JS/CSS/WASM; separate standalone assets under the existing MOS plugin route. Installed0.2.11 Home/Terminal/shared-editor and same-origin standalone workflows pass actual browser checks. VALIDATION.md owns evidence; publication still requires separate approval.
- Standalone: standalone.mjs mounts the same Plugin with requireAuthenticated. A server-verified MOS profile is mandatory before desktop mount; failure shows the MOS login link. Reuse same-origin authToken without copying credentials, adding an issuer or new login form. Both presentations share origin-local layout storage and its single-writer lock. Federation keeps host Vue; standalone bundles Vue separately. Private SDK editor source stays outside this repository; runtime/editor.mjs is a minified hash-pinned compiled artifact with dependency notices. PersonalEditor owns product Open/Save controls only, preserves text on conflicts, and explicitly does not persist unsaved drafts.
- Personal surfaces: desktop-personal owns bounded fixed-target requests and host-injected document Open/Save/Save As. No credentials go into configs/layouts or editor handles. Home supports top-level optimistic version-checked atomic Save and NOREPLACE Save As; conflict preserves text. backend/README.md owns the approved native-writer race limitation. Terminal configs persist bounded opaque session/generation references through the existing identity-fenced layout authority; refresh reattaches, never creates a replacement shell. Closing/hiding detaches and drops pending input, explicit confirmed End is separate. xterm6 has no clipboard addon or link-opening handler. Local browser fixture and real Linux service tests complement, not replace, live MOS admission. Read ../backend/AGENTS.md before changing the boundary.
- Request budget: personal views share80ms request-start spacing; bridge pacing also covers multiple clients while rechecking MOS identity every time. Preserve explicit rateLimited versus unauthenticated errors. Output reads may back off; uncertain input is never replayed. Terminal detach aborts input waiting for its request slot, drops unsent text and preserves backend jobs.
- Routes: None.
- Optional design: runtime/design holds three reviewed CSS assets and transformed identity. DesktopShell imports them at its `.desktop-root` boundary. No Astryx or new component system; host surface/on-surface variables inherit, standalone has explicit dark/system-font defaults. Preserve rectangular workspace hit testing, positioned shell geometry, remote iframe isolation and mounted editor/terminal identity. DESIGN-INTEGRATION.md and tests/design-ui.cjs own the scoped browser evidence. scripts/prepare-design.mjs is private authoring tooling, not a deployed SDK dependency.
- Batch publication: controller.dispatchBatch stages at most 1024 existing reducer commands privately under the same serialized queue, publishes one final snapshot only after all accept, and accumulates events. Rejection exposes no intermediate snapshot. Single dispatch preserves generated result identity. Persistence stores related host intentions in one v2 record as described below; no raw snapshot or crash-durable multi-key transaction is implied.
- Optional arrangements: desktop-arrangement composes approved SDK operations only; the app owns Tile/Tab/Freeform presets and explicit docking preview. Batch publication carries arrangement/projection through the same onChange as its accepted snapshot. DOM keys remain stable; host projection hides inactive tabs without erasing user visibility/minimization. Minimized active tabs fall back to eligible members. Clock draft settings are transient and retained across arrangement renders, not persisted until Apply.
- Arrangement storage: bounded v2 window/config/focus plus SDK intent goes in one `mos-desktop:layout:2:<scope>` record; prefer it on read, fall back to v1, and retain v1 untouched after opting in. Both versions use the existing v1 Web Lock/credential fences. SDK restore/remapped membership must pass before saving; failed/future recovery preserves records. Do not describe localStorage intentions as raw snapshot persistence, backend sessions or crash-durable multi-key transactions. The installed 0.2.3 rollback ignores v2 and restores its retained v1 record.
- M2 controls: desktop-mos owns fixed credential-fenced container reads and mos-desktop-only start/stop POSTs through controlDesktopContainer. MOS remains authorization/execution authority. No arbitrary target, command, URL or mutation adapter. Explicit UI confirmation warns Stop ends running apps/terminals; serialize pending requests and never retry uncertain outcomes automatically. Reads pause/clear on hide/close. Closing a view never initiates cancellation or reversal of a submitted MOS operation. Prior testit installed canary accepted; 0.2.2 renamed target has 29/29 Windows/Linux checks but awaits installed update. VALIDATION.md owns live evidence. M3 provisioning does not mean file/terminal service readiness.
- HTTP/geometry: createDesktopId uses randomUUID when available or cryptographic getRandomValues UUID-v4 bytes, never Math.random. HTTP LAN startup is supported but Web Locks absence keeps layouts memory-only; storage remains origin-local. Measure the actual positive workspace dimensions before recovering saved bounds; zero-sized/hidden mounts must not rewrite saved intentions against fallback dimensions. Completed move/resize release commits and recovers bounds, then flushes autosave immediately through the serialized action queue; other changes retain the short debounce. Preview/cancel never persist uncommitted geometry. Successful writes report an increasing count; Retry autosave appears only after write failure. Missing profile, storage and locking have distinct actionable messages; never bypass identity/single-writer gates to make the status green.
- Local shell candidate: ShellLayout.vue composes actual SDK345506c shell/profile/DOM APIs from separately staged runtime/shell assets. desktop-shell-template owns product labels/registrations; no alternative geometry solver. Existing host queue admits launch/reveal and retains existing identities/bounds/content. Transient dismissal never closes applications. Shell authoring lock is separate from normal application interaction.
- Shell persistence: desktop-shell-storage uses per-operation exclusive Web Locks and synchronous localStorage publication for atomic same-origin cross-view CAS, under the existing verified scope/credential fence. Separate mos-desktop:shell:1:<scope> records leave layout1/2 intact. Failed acknowledgements read back under the same lock; unresolved outcomes disable saves until reload. Unsupported records/imports remain recoverable, without destructive reset/save. Storage is origin/browser-profile local, not cross-device server storage. No Web Locks means no durable authoring.
- Shell coordinates: unscaled DOM workspace only; transformed/zoomed ancestors or visualViewport scaling disable shell projection/actions explicitly. No native-DPI support is implied. Shift-drag or Shift-arrows resize; arrows move; reorder changes SDK priority/tab order within fixed grid cells. See ../SHELL-INTEGRATION.md for local evidence. Owner-approved compiled frontend0.2.15 is installed on both hosts; ../DESIGN-INTEGRATION.md owns live design/layout smoke and retained0.2.14 rollback. Full installed shell authoring/backend connector acceptance remains separate.
- Catalog candidate: `../APPLICATION-CATALOG.md` owns unreleased library/Start/picker, injected adapters, fixed Home data discovery and opt-in connector approval/activation. One compiled pure catalog describes definitions; existing controller/WASM own app/window state. Active registrations/artifacts are pinned; missing saved applications preserve records and disable autosave. `shell:true` registrations retain the original authored shell template. Browser capabilities are the disclosed opaque-iframe subset; no strict origin/history/profile claims. Installed code runs only in an opaque sandbox after exact host approval and explicit activation, through unchanged createContentBinding; never evaluate it in the authenticated parent. Packaging is now disabled pending separately approved version/deployment.
- When a catalog update changes admitted single/multiple semantics with live instances, show deferred availability until all windows close; then reconcile the semantic definition on next launch. Reactive snapshot availability preserves drafts without advertising reducer-rejected launches.
